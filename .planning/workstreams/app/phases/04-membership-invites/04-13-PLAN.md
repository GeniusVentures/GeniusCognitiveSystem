<objective>
Make `RedeemInvite` a state-preserving merge instead of an unconditional full-state overwrite, and make it reject a tombstoned wallet.

Purpose: closes CR-01 and CR-02 (VERIFICATION truths 5, 29, 30). Today `RedeemInvite` (gcs_membership.cpp:763-943) builds a fresh `chat::MemberRecord` with the invite's role, `deleted=false`, and cleared `approved_by`/`pending_action`/`pending_role`, then calls `WriteMember`. Two failures follow: (a) a member with a D-07 dormant removal who redeems any invite silently cancels the pending removal and takes the invite's role (an approval bypass); (b) a removed (tombstoned) wallet resurrects itself with an old link. Both bypass the Super Admin approval model that MEMB-04 exists to enforce.

Output: a redeem path that reads the redeemer's stored record immediately after the authenticator gate and before the unwrap loop, rejects a tombstone with no write at all, and otherwise updates only the carried key material of an existing live record; plus negative regression tests that capture the stored bytes before the rejected redeem.
</objective>

## Interfaces the executor needs

From `src/lib/gcs_membership.cpp` (current, exact shape of the write block to replace):

- `TryReadMember( const std::string &scopeId, const std::string &address, chat::MemberRecord &out ) const` — returns true when a parseable record exists; tombstoned records STILL return true (the caller decides).
- `WriteMember( const chat::MemberRecord &record )` — full-state Put under `MemberKey(...)`, preserves `created_at_ms`, re-stamps `updated_at_ms`.
- `Membership::m_sender` — the redeemer's wallet address (the record key).
- The authenticator gate (878-896) precedes both the unwrap loop (900-916) and the write block (918-943). The tombstone read/reject must be inserted immediately after the authenticator gate, BEFORE the unwrap loop — the unwrap loop calls `crypto::StoreRoomKey`, so a rejection placed at the write block would still have written process-local key state.

From `src/lib/gcs_membership.hpp`:

- `static constexpr const char *kMembersKeyPrefix = "gcs/members/";` — PUBLIC (line 103).
- `static std::string MemberKey( const std::string &scopeId, const std::string &address );` — PRIVATE (line 324). It is `kMembersKeyPrefix + scopeId + "/" + address`. Tests must NOT call it; build the key from the public prefix, as the existing `ReadMemberRecord`/`SeedMember` helpers already do.

From `src/proto/gcs_chat.proto` `MemberRecord` (237-249): `scope_id`, `address`, `role`, `deleted`, `created_at_ms`, `updated_at_ms`, `approved_by`, `pending_action`, `pending_role`, `explicit_leave`, `wrapped_room_key`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Invite URL (out of band, untrusted) → `RedeemInvite` | Any holder of an old link can replay it; the link is not a membership grant by itself |
| CRDT store → `RedeemInvite` | The redeemer's existing member record is read from a store that any peer may write |
| `RedeemInvite` → member record write | The redeem path mutates the roster the D-07 approval model protects |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-13-01 | Elevation of privilege | Redeem cancelling a dormant removal (`approved_by` cleared, `pending_action` reset) | mitigate | Merge into the stored record and touch only `wrapped_room_key`; `DormantRemovalSurvivesRedeem` pins the stored role/pending state (Task 1-2) |
| T-04-13-02 | Spoofing | Removed (tombstoned) wallet resurrects with a stale link | mitigate | `TryReadMember` + `existing.deleted()` rejection immediately after the authenticator gate and before the unwrap loop, so neither a member record nor a room key is written; `TombstonedMemberCannotRedeemStaleInvite` captures the baseline bytes (Task 1-2) |
| T-04-13-03 | Tampering | Redeem rewriting a member's role to the invite's grant | mitigate | The live branch never calls `set_role`; only the no-record (new member) branch applies the invite role |
| T-04-13-04 | Information disclosure | Rejected redeem leaking whether a wallet is tombstoned | accept | The rejection happens after the bearer-authenticator gate, so only a holder of a valid invite can probe; the response is the same generic error as every other rejection |
| T-04-13-05 | Denial of service | A rejected tombstoned redeem blocking future legitimate re-invites | accept | Out of scope: a genuine re-invite flow would require an explicit reactivation decision (D-03 tombstone semantics); no Phase 4 requirement asks for it |
| T-04-13-SC | Tampering | Package-manager installs | accept | No new dependency is introduced by this plan; nothing to audit |
</threat_model>
