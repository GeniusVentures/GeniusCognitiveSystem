## Locked decisions this plan implements

- **D-07** (dormant-until-approved): "admin demotion, member removal, space/room deletion" are the Phase 4 destructive set; when 2+ admins exist the author writes the op dormant with an empty `approved_by`.
- **D-08** (permission matrix): the five tiers gate actions at C++ write time; higher tiers govern lower ones.
- **D-05** (bearer key in the URL): `gcs://invite/{space|room}/<id>?key=<key>`; the key doubles as the room-key delivery vehicle.
- **D-06** (key-wrap derivation): HKDF-SHA256 + AES-256-GCM on top of the vendored OpenSSL, behind an injectable seam; the FFI/Dart never call EVP.
- **D-01**: one `MemberRecord` per member per scope under `gcs/members/<scopeId>/<wallet>`, enumerated by prefix scan.
- **User decision (this revision)**: gate EVERY invite, including invites that carry no room-key material.

## Planner decisions the executor MUST follow (do not re-litigate)

1. **WR-03 predicate direction.** The VERIFICATION text writes `PrivilegeRank(record.role()) <= PrivilegeRank(ROLE_ADMIN)`. That literal form is wrong for the stated behaviour: a `SUPER_ADMIN` target has rank 5 and `5 <= 4` is false, so the bypass would survive. Implement the stated intent instead: a role change is a destructive admin demotion when the TARGET currently holds admin tier or above AND the change lowers its rank — i.e. `PrivilegeRank(record.role()) >= PrivilegeRank(chat::ROLE_ADMIN) && PrivilegeRank(role) < PrivilegeRank(record.role())`. A Member/Guest demotion stays non-destructive (not in the D-07 set). The creator remains protected separately by `CanChangeRole` (MEMB-03).
2. **WR-02 strict outrank.** The author must strictly outrank the target. Consequence (accepted): the creator (rank 5) cannot remove a second, non-creator Super Admin (rank 5) directly; the creator demotes that member first via `ChangeRole` (which `CanChangeRole` permits unconditionally for a Super Admin author) and then removes them.
3. **WR-04 scope-kind cross-check without a local entity record.** Do NOT resolve the scope against the catalog to check the kind: in the cross-node redeem case the redeemer legitimately has no entity record for the scope (see `test/test_gcs_membership_multinode.cpp`), and requiring `ResolveScope().found` would break it. Instead stamp the kind on the invite record at mint (`InviteRecord.is_space`) and compare the URL kind against that stamp.
4. **WR-04 every-invite gate (user decision).** The authenticator is authoritative for ALL invites: `RedeemInvite` verifies it BEFORE writing the member record, whether or not the record carries wrapped room keys. The wrapped-room-key unwrap loop keeps its existing skip-and-log posture (it delivers key material, not authority). When the seam is disabled (`InviteAuthEnabled()` false — the pre-D-06/test-only posture, symmetric with the existing `KeyWrapEnabled()` handling) the gate is skipped; production always enables it.
5. **WR-06 topic design.** A recipient by definition has NOT joined the invited scope, so per-scope topics cannot deliver an invite: member/invite records must replicate on a topic every node subscribes to. Change `ScopeTopics` to broadcast on one well-known membership topic, exposed as `Membership::kMembershipTopic`, and move the multinode fixture onto it IN THIS PLAN (the fixture's per-room registration is deleted, because keeping it would both hide the gap and leave the suite red until 04-12).
6. **Both proto fields plus the authenticator land here, in wave 5.** `InviteRecord.is_space`, `InviteRecord.authenticator`, and `InviteLink.scope_id` are appended in this plan so the two wave-6 consumers (04-10 Dart regen, 04-11 FFI push + seam wiring) can regenerate/consume them independently. `Membership::MintInvite` returns only the URL string, so it never sets `InviteLink.scope_id` — the FFI does (04-11). The authenticator never travels in the URL: the redeemer derives its verification from the bearer key already present in the query.
