<objective>
Bring the membership unit suite onto the signed-record contract and add regression tests for the trust chain and the authority transition matrix.

Purpose: 04-19 makes unsigned records non-members. Every existing `SeedMember` call writes an unsigned record, and the two `OnMemberArrived` deliveries in `DeleteScopeTombstonesEntityAndOnMemberArrivedPushes` are unsigned as well, so the suite would fail for the wrong reason. This plan signs the seed and arrival paths with a single shared helper (test-side invariant 11: one builder, never copied), flips the expectations that asserted the pre-signing model, and pins the new contract: forged records are excluded, self-signed records are Guest-capped, a creator-target or admin-tier bypass is rejected, strict outrank uses the signed predecessor, flipped leaves and replays are rejected, and legitimate leave/redeem preserve authority.

Output: `test/test_gcs_member_helpers.hpp`; a signed `SeedMember` and signed arrival records; rewritten peer-SUPER_ADMIN cases; and fifteen new trust-chain tests.

## Why the suite is red before this plan

- `SeedMember` (`test_gcs_membership.cpp:387-404`) Puts a record with no `created_by`/`record_signature`. After 04-19, `TryReadMember`, `MembersFor`, `LocalRoleFor`, and `AdminCount` reject it, so every seeded test resolves its subjects as absent.
- `DeleteScopeTombstonesEntityAndOnMemberArrivedPushes` (`:1405-1444`) builds `arrived` and `deadArrived` as raw `MemberRecord`s and feeds them to `OnMemberArrived`. After 04-19 T3(i), both deliveries fail verification and no roster is pushed, so both `ASSERT_GT(events.size(), before)` fail. `deadArrived` also copies `address = kMemberAddress` while the callback key names `kDeadAddress`, so it fails the body/key binding even if signed.
- `MintRejectedWhenIssuerSeamIsDisabled` (`:798-835`) asserts `noIssuer.OnScopeCreated(...)` SUCCEEDS. 04-19 makes `WriteMemberAsAuthor` fail closed without the issuer seam.
- Three tests seed a non-creator `ROLE_SUPER_ADMIN` target (`:1639`, `:1763`, `:1799`). The new third-party rule forbids granting SUPER_ADMIN, so those records are now unverifiable by design. They must become rejection cases or change the target role.
- Seed records are fresh creator grants (`prior_role == ROLE_UNSPECIFIED`); a seeded tombstone must carry `prior_role == role`, and any seeded `explicit_leave` needs a subject `leave_signature`. The helper sets both.

## Interfaces the executor needs

- `MakeSeam( signerAddress, issuerEnabled )` (`:354-379`) — the test double's `sign` returns `"testsig:" + signerAddress + ":" + payload` and `verifyIssuer` accepts only that exact token for the claimed issuer. A signature is therefore constructible without a live Membership instance.
- `TestIssuerSignatureHex( issuer, payload )` (`:103`) — `crypto::HexEncode` of the double's token.
- `ReadMemberRecord` (`:210`) — a RAW store read; it ignores verification and is the right tool to prove exclusion-without-deletion.
- `FindMember`, `RoleOf`-style helpers, `kSeedCreatedAtMs`.
- The invite helper precedent `test/test_gcs_invite_helpers.hpp` — header-only, one builder, mirrors production exactly.
- `kTestCreatorAddress`, `kMemberAddress`, `kTargetAddress`, `kGuestAddress`, `kDeadAddress` — the fixture identities.
- `SeedMember`'s current signature is `( scopeId, address, role, createdAtMs = kSeedCreatedAtMs, deleted = false )`. The new `signer` parameter is added LAST so every existing call remains source-compatible; a hostile signer is supplied as the sixth argument.

## Canonical member payload (must mirror 04-19 exactly)

Domain `"gcs-member-issuer-v1"` + `'\n'` + scope id + `'\n'` + address + `'\n'` + serialized record with `record_signature`, `leave_signature`, `wrapped_room_key`, and `explicit_leave` cleared; `created_at_ms`, `updated_at_ms`, and `prior_role` KEPT.

## Canonical leave payload (must mirror 04-19 exactly)

Domain `"gcs-member-leave-v1"` + `'\n'` + scope id + `'\n'` + address. Signed by the SUBJECT, hex-encoded into `leave_signature`.

## Per-key LWW and rejection semantics (do not mis-assert)

A hostile record Put on a wallet's key is the winning LWW value even when verification rejects it. Therefore, while the hostile bytes are in the store, that wallet is ABSENT from `MembersFor` (not "still the previous role"), and a `Membership` bound to it resolves GUEST. Rejection prevents escalation; it does not roll the key back. To prove the valid chain still wins, save the subject's creator-signed bytes before the hostile write, re-Put them after the assertions, and then assert the previous verified role is restored (the identical signature hits the predecessor cache's same-write path, so it is accepted). Every exclusion test follows this save/hostile/assert/restore/assert pattern where a subject had a prior valid record.

- Do NOT touch the multinode suite (04-22) or the command-path defect tests (04-21).
- Do NOT use `std::this_thread::sleep_for` / `sleep_until`.
