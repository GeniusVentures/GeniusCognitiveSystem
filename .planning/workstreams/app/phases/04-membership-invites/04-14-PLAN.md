<objective>
Give the EntityStore a deletion-class mutator and route `DeleteScope`/`Approve`'s entity branch through it, so the in-memory catalog never goes stale; make `AdminCount` fail closed.

Purpose: closes CR-06 (VERIFICATION truth 11). `DeleteScope` (gcs_membership.cpp:1058-1124) writes the pending/tombstoned `SpaceRecord`/`RoomRecord` with a raw `m_session.Put` and never updates `m_spaces`/`m_rooms`. `Approve` (1126-1231) then iterates `m_entities.Spaces()`/`Rooms()` — which still hold the pre-delete live records — so it never sees `pending_action() == PENDING_ACTION_DELETE`, breaks out, and rejects the approval. `PushSpaceTree` re-emits the stale live scope in the same window. Separately, `AdminCount` (370-396) returns 0 when the scan fails, which makes "2+ admins" read as "one admin" and takes the immediate-destructive branch — a fail-open on the approval gate. All three are the same class: the catalog and the count disagree with the authoritative store.

Output: two symmetric EntityStore mutators (`ApplySpaceState`, `ApplyRoomState`) that Put the caller's full record and then publish it to the catalog under `m_catalogMutex` (never held across the Put); `DeleteScope` and `Approve` routed through them, pushing only after the catalog swap; `AdminCount` returning `outcome::result<unsigned int>` with all three call sites propagating; plus unit and membership regression tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FFI command (`delete_scope` / `approve`) → `Membership` | Untrusted caller identity is already gated by `CanDelete`/`CanApprove`; the gap is what the accepted caller writes |
| `Membership` → `EntityStore` catalog | The catalog drives `PushSpaceTree`; a stale entry is a live view the store no longer has |
| CRDT store → `EntityStore` catalog | The catalog is a cache of the session; divergence breaks the approval predicate |
| `m_catalogMutex` ↔ FFI `g_mutex` | Lock-order inversion deadlocks the DagWorker heal path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-14-01 | Denial of service | Holding `m_catalogMutex` across `m_session.Put` in the new mutators (ABBA vs `g_mutex`) | mitigate | Put first, catalog swap second, lock never nested; documented in the header; `ConcurrentCatalogReadsAndRoomCreatesDoNotRace` stays green |
| T-04-14-02 | Elevation of privilege | A failed admin scan reading as 0 admins, so a destructive action skips dormancy and activates immediately | mitigate | `AdminCount` returns `outcome::result<unsigned int>`; every caller propagates the error before deciding |
| T-04-14-03 | Tampering | Approve activating a record whose stored state is no longer dormant (remote write or replay) | mitigate | Re-read the authoritative session bytes and evaluate `approved_by`/`pending_action` there; the catalog is used only to learn the kind |
| T-04-14-04 | Spoofing | A stale live catalog entry re-emitted by `PushSpaceTree` after a delete | mitigate | Catalog swap happens inside the mutator before any push; `DeleteScopeDormantThenApproved` asserts the pushed tree excludes the approved scope |
| T-04-14-05 | Repudiation | Approver identity lost on the tombstone | mitigate | The approval stamps `approved_by( m_sender )` and persists it through the same mutator |
| T-04-14-SC | Tampering | Package-manager installs | accept | No new dependency is introduced by this plan; nothing to audit |
</threat_model>
