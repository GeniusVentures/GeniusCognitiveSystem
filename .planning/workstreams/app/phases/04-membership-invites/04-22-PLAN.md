## Per-key LWW and rejection semantics (do not mis-assert)

A hostile record Put on a wallet's key becomes the winning LWW value even when verification rejects it. Therefore, while the hostile bytes are in the store, that wallet is ABSENT from `MembersFor` and `RoleOf` returns `ROLE_UNSPECIFIED` — it is NOT "still the previous role". Rejection prevents escalation; it does not roll the key back.

Every authority-transition case therefore follows this sequence:

1. Save the target's current creator-signed bytes (raw `Get` on `kMembersKeyPrefix + roomId + "/" + target`).
2. Publish the hostile record and wait until BOTH nodes' raw key holds it.
3. Assert the hostile bytes are the winning value, the target is absent from `MembersFor`, and no command authority was gained.
4. Re-Put the saved creator-signed bytes through `kMembershipTopic`, wait for both raw keys, and assert the target's original verified role is restored. The identical signature takes the predecessor cache's same-write path, so it is accepted without needing a newer timestamp.

Restoration is the test publishing the creator's own bytes, not a claim of attacker authority.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public membership topic → both nodes | Any peer may publish a member record under any wallet key |
| Real signer → claimed wallet | The signature proves key possession; it does not by itself prove role authority or a permitted transition |
