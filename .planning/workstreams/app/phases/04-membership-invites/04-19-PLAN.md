<objective>
Make the member record an authenticated authority artifact: append `created_by`, `record_signature`, `leave_signature`, and `prior_role`; sign every write path; verify every read path and authorization decision; and enforce an authority transition matrix that cannot be bypassed by publishing a validly signed record on the permissionless topic.

Purpose: closes truth 29's first three clauses and truth 5's wire-level approval bypass (VERIFICATION.md). Today `MemberRecord` is unauthenticated: any peer may publish `ROLE_SUPER_ADMIN` for its own wallet on the permissionless membership topic, and `MembersFor`, `TryReadMember`, `LocalRoleFor`, `AdminCount`, and `OnMemberArrived` accept it. Signatures alone are not enough: a validly signed record could still overwrite the creator, tombstone or demote a peer Admin without the D-07 approval, demote a peer Moderator below strict outrank, or flip `explicit_leave` on another wallet. This plan therefore adds (a) an unconditional creator-target rejection, (b) strict outrank against the target's signed `prior_role` (including for dormant requests), (c) a creator gate on every admin-tier demotion/tombstone/dormant request, (d) a subject-signed leave, and (e) a predecessor check that makes a replayed or mis-declared prior state fail closed once the node has verified the newer state.

Output: append-only proto fields 12/13/14/15; canonical member and leave payloads; sign/verify primitives; author-signed versus authority-preserving write paths; verified read paths; an authority transition matrix; and a local verified-predecessor guard.
</objective>

## Authority holes this plan closes

A signature proves key possession, not authority. Each of these records is validly signed by the wallet it names and must still be rejected:

- A Moderator signs a record at the creator's key setting `role = ROLE_GUEST`. Grant matrix alone passes; the creator-target check must reject it unconditionally.
- An Admin signs `deleted = true`, an applied `role = MODERATOR` from a prior `ADMIN`, or a dormant pending REMOVE/ROLE_CHANGE for a peer Admin. The command layer rejects an Admin acting on a peer Admin (strict outrank), so verification must too: **every** admin-tier destructive or dormant transition requires the creator, who is the only role above ADMIN.
- A Moderator signs `role = MEMBER` for a peer Moderator. Grant matrix alone passes; strict outrank against the signed `prior_role` must reject it.
- Any peer copies a valid record for another wallet and flips `explicit_leave`. The authority payload excludes it; a separate subject signature must make the flip unverifiable.
- A peer republishes an older validly signed state (pre-demotion, pre-tombstone). The signed `prior_role` plus the node's verified-predecessor cache must reject it once the newer state has been verified.

## Canonical member payload (the contract to implement)

- Signing covers the AUTHORITY fields only: `scope_id`, `address`, `role`, `deleted`, `approved_by`, `pending_action`, `pending_role`, `created_by`, `created_at_ms`, `updated_at_ms`, `prior_role`.
- The canonical copy clears `record_signature` (a signature cannot cover itself), `leave_signature` (a separate subject signature over its own payload), `wrapped_room_key` (bearer key material refreshed at redeem, never authority), and `explicit_leave` (a subject transition covered by `leave_signature`, D-02).
- `created_at_ms` IS signed: it is immutable after the first write, so including it prevents a rewritten history.
- `updated_at_ms` IS signed: authority writes stamp it before signing; authority-preserving writes preserve the stored value verbatim, so the signature stays valid without re-signing. Its inclusion prevents an attacker from re-dating a captured record.
- `prior_role` IS signed: exactly one write helper sets it from the verified stored record, so the transition matrix has an authenticated predecessor claim.
- Payload shape: domain + `'\n'` + scope id + `'\n'` + wallet address + `'\n'` + serialized canonical record. The explicit scope/address binding prevents moving a valid record onto another key.
- `record_signature` is `HexEncode(raw signature bytes)`.

## Canonical leave payload

- Domain `"gcs-member-leave-v1"` + `'\n'` + scope id + `'\n'` + subject address. It attests only "this wallet leaves this scope".
- It is signed by the SUBJECT (`m_sender` in `Leave`), not by the authority signer. `leave_signature` is hex.
- Verification: `explicit_leave == true` requires a valid subject signature; `explicit_leave == false` requires `leave_signature` to be empty. An attacker can copy a record but cannot mint the subject's signature, so a flipped flag is rejected.
- It deliberately does NOT bind the authority signature: a later authority rewrite cannot invalidate the subject's leave, and no non-subject wallet needs to re-sign it.

|----------|-------------|
| Permissionless membership replication topic → Membership roster | Any peer can publish bytes under `gcs/members/<scope>/<wallet>`; nothing authenticates the writer at the transport |
