  <how-to-verify>
    1. Build and launch two instances of the Flutter app (macOS or desktop) pointed at the same shared session/room. Two live instances are required — cross-peer delivery (SC2) cannot be verified with a single instance, so no single-instance fallback is accepted.
    2. In instance A, select a joined room and send a message containing a unique marker string (e.g. `D08PROBE12345`) from the composer. Confirm: the message appears immediately at 40% opacity (pending) then solidifies (complete), aligned trailing (user_self accent), with no sender label.
    3. In instance B (same room), confirm the message appears without any manual refresh, aligned leading (user_peer), with a truncated sender label (`0x` + short-form, never the full 130-char address) above the bubble. If both instances render the message, the encrypted envelope was published, delivered, and decrypted correctly end-to-end (D-08 live path).
    4. Send a second message from instance B; confirm instance A receives it and renders it as a peer (leading).
    5. Restart both instances and rejoin the same room; confirm the full message history replays in chronological order (oldest top -> newest bottom) with the same order on both instances, AND that replayed messages sent by the OTHER instance render as leading peers with a truncated `0x` sender label while replayed messages sent by THIS instance render trailing with no sender label (per-message sender identification — D-04/SC4). History replay proving out on both instances also proves both sides decrypt the archived envelopes (D-08 scan path).
    6. Trigger a transport failure (e.g. send while disconnected) and confirm the message shows the terminal error tint (#FF4D4D at 12% alpha) with a "Send failed" toast, and that re-sending manually creates a new message (no auto-retry).
    7. At-rest opacity check (D-08): while the room still displays the marker message from step 2, locate the running instance's GlobalDB rocksdb directory (the db_path configured at gcs_init — printed at startup / under the app's application-support directory; `grep -rn "db_path\|globaldb" src/ffi/gcs_core_ffi.cpp` shows the default if unsure), then run `grep -r --binary-files=text "D08PROBE12345" <globaldb-dir>` — it must return ZERO matches. The plaintext exists only in memory and in the pushed decrypted events, never on disk (records are nonce||ciphertext||tag envelopes). Optionally also run it on the SECOND instance's db dir: zero matches there too (receivers archive the envelope as received).
  </how-to-verify>
  <acceptance_criteria>
    - Local echo shows pending -> complete with no duplicate.
    - Cross-instance delivery happens with no manual refresh.
    - Peer bubbles show a truncated `0x` sender label; self bubbles show none.
    - History order is identical across both instances after restart.
    - Replayed history shows per-message sender identification: peer messages carry a truncated sender label, self messages carry none.
    - Failed send shows the terminal error tint + "Send failed" toast with manual (not automatic) re-send.
    - `grep -r --binary-files=text` for the known message marker over both instances' GlobalDB directories returns zero hits (D-08 at-rest opacity).
  </acceptance_criteria>
