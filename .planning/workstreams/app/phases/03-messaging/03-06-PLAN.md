  <what-built>The full Phase 3 messaging path: C++ Messaging component (send/receive/dedupe/history), FFI wiring, and the Dart cubits (upsert, messageHistory replaceAll, sender label).</what-built>
  <action>
    Build and launch two instances of the Flutter app (macOS or desktop) on the same session/room, then perform the verification steps below. Record "approved" or a punch list of issues.
  </action>
  <how-to-verify>
    1. Build and launch two instances of the Flutter app (macOS or desktop) pointed at the same shared session/room. Two live instances are required — cross-peer delivery (SC2) cannot be verified with a single instance, so no single-instance fallback is accepted.
    2. In instance A, select a joined room and send a message from the composer. Confirm: the message appears immediately at 40% opacity (pending) then solidifies (complete), aligned trailing (user_self accent), with no sender label.
    3. In instance B (same room), confirm the message appears without any manual refresh, aligned leading (user_peer), with a truncated sender label (`0x` + short-form, never the full 130-char address) above the bubble.
    4. Send a second message from instance B; confirm instance A receives it and renders it as a peer (leading).
    5. Restart both instances and rejoin the same room; confirm the full message history replays in chronological order (oldest top -> newest bottom) with the same order on both instances, AND that replayed messages sent by the OTHER instance render as leading peers with a truncated `0x` sender label while replayed messages sent by THIS instance render trailing with no sender label (per-message sender identification — D-04/SC4).
    6. Trigger a transport failure (e.g. send while disconnected) and confirm the message shows the terminal error tint (#FF4D4D at 12% alpha) with a "Send failed" toast, and that re-sending manually creates a new message (no auto-retry).
  </how-to-verify>
  <acceptance_criteria>
    - Local echo shows pending -> complete with no duplicate.
    - Cross-instance delivery happens with no manual refresh.
    - Peer bubbles show a truncated `0x` sender label; self bubbles show none.
    - History order is identical across both instances after restart.
    - Replayed history shows per-message sender identification: peer messages carry a truncated sender label, self messages carry none.
    - Failed send shows the terminal error tint + "Send failed" toast with manual (not automatic) re-send.
  </acceptance_criteria>
