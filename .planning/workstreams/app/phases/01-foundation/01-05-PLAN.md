<objective>
Close the Dart NativePort gap identified in RESEARCH Open Question 1: implement the standard
Dart API_DL pattern (`Dart_InitializeApiDL` + `Dart_PostCObject` + `ReceivePort`) inside gcs_ffi,
generate Dart bindings via ffigen, and prove the round-trip with a Dart-side smoke test.

Purpose: D-05 locks "push, don't poll" — network data flows C++ → Dart via NativePort. Without
this plan, the FFI surface is one-directional (Dart → C++ only) and Phase 3's messaging cannot
deliver incoming messages to Flutter.

This is the phase's only genuine "no in-repo precedent" work. The spike validates:
  1. Vendoring `dart_native_api.h` + `dart_api_dl.c` into src/ffi/ (the package:ffigen-documented
     approach) — vs. weak-linkage declare.
  2. Initializing the API_DL table at library load.
  3. Posting a string `Dart_CObject` to a registered port when a CRDT update arrives.

Output: working native→Dart callback path; Phase 3+ messaging plugs into it.
</objective>

Standard include strategy (the "vendored" pattern documented in package:ffigen):
  - Copy `dart_native_api.h` + `dart_api_dl.c` + `dart_api_dl.h` + `dart_version.h` from
    `$FLUTTER_ROOT/bin/cache/dart-sdk/include/` into `src/ffi/`.
  - In gcs_core_ffi.cpp's translation unit, call `Dart_InitializeApiDL(NativeMajorVersion, ...)`
    once at first gcs_init — or via a library-load hook if available.
  -dart_api_dl.c provides the Dart_PostCObject symbol indirection.

C-side posting shape:
```c
Dart_CObject message;
message.type = Dart_CObject_kString;
message.value.as_string = const_cast<char*>(utf8_payload);
Dart_PostCObject(port, &message);
```

Dart-side receive shape:
```dart
final receivePort = ReceivePort();
bindings.gcs_on_message(handle, receivePort.sendPort.nativePort);
receivePort.listen((msg) { /* msg is String */ });
```

ffigen mapping: `int64_t` ↔ Dart `int`, `GcsSession*` ↔ `Pointer<GcsSession>` (opaque struct).
