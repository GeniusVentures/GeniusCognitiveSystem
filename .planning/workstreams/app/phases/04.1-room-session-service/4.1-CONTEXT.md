<decisions>
## Implementation Decisions

### Boundary shape (owner ruling, mapped from genius-tube 2.2)
- **D-30:** The app and the lib must never include FFI headers — "the app
  should never include any ffi header files, as ../apps/genius-tube is doing."
  In GCS this is ALREADY structurally true and the phase's job is to keep it
  true while the rules move: `src/lib` includes nothing from `src/ffi`
  (verified 2026-11-03 — `gcs_core.hpp` in lib ≠ `gcs_core.h` in ffi), and
  Dart binds exclusively via `ffigen.yaml` → `gcs_bindings_generated.dart`
  over the one C-ABI header `src/ffi/gcs_core.h`. Unlike genius-tube's D-41,
  GCS needs NO two-library split — the disease is inverted (the audit: the
  adapter duplicated domain rules, not domain TUs including FFI headers).
  The GCS enforcement of this boundary is compiler-level linkage, not a
  scanner: service tests link `gcs_core` WITHOUT `gcs_ffi` (D-33 below).
- **D-31 (genius-tube D-44 transplant):** The service surfaces session state
  through a constructor-injected, domain-typed seam — registered-rooms changes
  are plain C++ typed values, no Dart/wire/pb types inside `src/lib`. The FFI
  installs the PostToDart-backed sink at `gcs_init` and owns all translation
  (event-kind mapping, payload fill) in the adapter. This is the mechanism
  that lets the registry move without dragging FFI knowledge down with it.
- **D-32 (ABI/payload freeze):** `src/ffi/gcs_core.h` and every pushed event
  payload byte are untouched. Zero ABI churn, zero proto changes. The
  observable contract (error results, event ordering, payloads) is identical
  before/after — genius-tube's D-43 enum change was a sanctioned behavior
  change THERE; v1.0.1's gate forbids it here.

### Ordering and discipline
- **D-33 (test placement + linkage, resolves the 4.1-vs-4.4 question):** The
  service's unit tests land with Phase 4.1 linked against `gcs_core` WITHOUT
  `gcs_ffi`, following the existing precedent
  (`test/CMakeLists.txt:113,129` — test_gcs_entities / test_gcs_membership
  already link `gcs_core;gcs_storage;neoswarm_common`). Phase 4.4's CPLX-08
  target remains the FORMAL lib-only lifecycle + tripwire target; 4.1 does not
  build it, 4.1 just writes tests that will move there without edits.
- **D-34 (remediate first, gate last):** genius-tube D-41's ordering ruling
  applies — the service move lands on its own; enforcement targets/tripwires
  land in 4.4 on the clean tree. No CMake restructure beyond what the service
  target needs.
- **D-35 (lock discipline):** The service follows the established
  `m_catalogMutex` pattern (T-04-14-01): no lib-held lock spans a CoreSession
  Put/Get; accessors lock internally and return by value. The FFI g_mutex
  lock-order contract is unchanged.
- **D-36 (push sequencing preserved):** The FFI's recompute-then-push
  sequence — RefreshDerivedJoins-equivalent → SpaceTree → RoomList in one
  publish — is preserved exactly; it is observable event ordering (Phase 02
  decision). The service computes; the FFI still pushes in the same order.

### Claude's Discretion
- Exact service name/file layout in `src/lib` (e.g. `gcs_room_session.hpp/.cpp`)
  and whether the registry is one class or composes over EntityStore/Membership.
- Seam signature shape (callback vs sink interface) — must stay a plain C++
  domain type per D-31; no locator ceremony, constructor injection per repo
  idiom.
- How much of the FFI's per-arm validation stays in the adapter (argument
  null/empty checks) vs moves to the service — the contract is only that the
  adapter stops computing rank/policy/join expressions (CPLX-02).
